# Deploying the live site (Phase 19)

One website on Render's free plan, data on Neon's free plan:

```
browser ──https──> Render (one Docker container)                 Neon (PostgreSQL 17 + pgvector)
                     FastAPI: /api/...  the API          ──SQL──>  the same tables as on the laptop
                              /...      the React app
```

The container is built from the `Dockerfile` in the repo root; `render.yaml` describes the service.
The live site is **read-only**: data is collected on the laptop (ingest, metrics, labels, LLM, RAG) and
copied up with `scripts/copy-db-to-neon.sh`. The site never calls GitHub's data API or Gemini, and needs no
Gemini key. Visitors can open the demo (`encode/httpx`) without logging in; GitHub login shows your own
repositories.

Free-plan behaviour to know before a demo: Render stops the container after 15 idle minutes and the next
visit takes about a minute to wake it, so open the site a few minutes early. Neon also pauses an idle
database; the app reconnects by itself.

## 0. Before deploying (on the laptop, once)

After merging the Phase 19 pull request:

```
cd backend
source venv/bin/activate
python -m database.migrate                      # adds pr_labels.evidence
python scripts/add_label_evidence.py encode/httpx   # stores which later PR fixed each risky PR; changes no label
```

The second command stops and writes nothing if any recomputed label differs from the stored one.

## 1. Neon: the database

1. Sign up at neon.com (GitHub login works, no card needed).
2. Create a project: name `pr-risk`, PostgreSQL 17, region **AWS Asia Pacific (Singapore)**,
   the closest to Render's Singapore region.
3. Open **Connect**, turn **Connection pooling off**, and copy the connection string
   (`postgresql://...neon.tech/neondb?sslmode=require...`). Keep it out of chats and commits.
4. Copy the data up (asks for the string, does not show or save it):

```
scripts/copy-db-to-neon.sh
```

It copies every table except the users table; of users only the repository owner's id, GitHub id and
username go up (no email, no GitHub token). It turns on pgvector, refuses to overwrite a database that
already has tables unless run as `REPLACE=yes scripts/copy-db-to-neon.sh`, and prints the row counts at the
end (expected: pull_requests 1822, pr_labels 5428, llm_analyses 780, document_chunks 185).

## 2. GitHub: a second OAuth app for the live site

Keep the laptop's OAuth app as it is and make a new one, so the live site's secret is never on the laptop.
github.com/settings/developers > OAuth Apps > New OAuth App:

- Application name: `PR Risk`
- Homepage URL: `https://pr-risk.onrender.com`
- Authorization callback URL: `https://pr-risk.onrender.com/api/auth/callback`

Then **Generate a new client secret** and keep the page open for step 3.
(If Render gives the site a different address in step 3, come back and change both URLs.)

## 3. Render: the website

1. Sign up at render.com with GitHub and allow access to the `pr-risk-analysis-platform` repository.
2. **New > Blueprint**, pick the repository. Render reads `render.yaml` and asks for these values:

| Setting | Value |
| --- | --- |
| `DATABASE_URL` | the Neon connection string from step 1 |
| `GITHUB_CLIENT_ID` | from the new OAuth app |
| `GITHUB_CLIENT_SECRET` | from the new OAuth app |
| `GITHUB_REDIRECT_URI` | `https://pr-risk.onrender.com/api/auth/callback` |
| `FRONTEND_URL` | `https://pr-risk.onrender.com` |

   `JWT_SECRET_KEY` and `TOKEN_ENCRYPTION_KEY` are generated by Render (new random values, never the
   laptop's). The rest is in `render.yaml`.
3. Apply. The first build takes several minutes. The address is at the top of the service page; if it is
   not `pr-risk.onrender.com`, change `GITHUB_REDIRECT_URI` and `FRONTEND_URL` under **Environment**, and
   both URLs in the OAuth app.

From then on every merge to `main` deploys by itself once the CI checks pass.

## 4. Check the live site

- `https://<site>/api/health` shows `{"status":"ok","database":"connected"}`.
- The start page loads and the risk map builds as you scroll.
- `/repos/encode/httpx` opens without logging in; PR #3394 shows the later fix (#3426).
- **Log in** returns to the same page with your username in the header.
- `/api/docs` opens Swagger; an unknown address shows the "page does not exist" page.

## Updating the data later

Collect on the laptop as usual, then `REPLACE=yes scripts/copy-db-to-neon.sh`. The site shows the new data at
once; no redeploy is needed.

## When something goes wrong

- **The deploy fails with "Not safe to start in production"** (Render > Logs): the lines below it name the
  setting to fix. This check is deliberate: the site refuses to start with a missing or weak setting.
- **GitHub says the redirect_uri is not associated with this application**: the OAuth app's callback URL
  and `GITHUB_REDIRECT_URI` differ. They must match exactly.
- **`/api/health` answers 503**: the site runs but cannot reach Neon; check `DATABASE_URL`.
- **Everyone is logged out after changing a secret**: expected; they log in again.

## Secrets: where each one lives

| Secret | Laptop (`backend/.env`) | Live site (Render) |
| --- | --- | --- |
| GitHub client id / secret | laptop OAuth app | the second OAuth app |
| `JWT_SECRET_KEY`, `TOKEN_ENCRYPTION_KEY` | laptop values | generated by Render |
| Database password | local PostgreSQL | inside the Neon connection string |
| `GEMINI_API_KEY` | yes (batch scripts) | not set: the site never calls Gemini |

`scripts/generate-prod-secrets.py` prints a new `JWT_SECRET_KEY` and `TOKEN_ENCRYPTION_KEY`, for a host
that cannot generate them.
